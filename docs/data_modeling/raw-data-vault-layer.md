RDV Layer - Overview
====================

* * * * *

#### 1\. Data Layer Structure and Entity Rules [](https://data-engineering-docs-52075d.pages.roche.com/docs/data-modeling/data-vault/raw-dv-layer/rdv-layer/#1-data-layer-structure-and-entity-rules)

This data layer is responsible for materializing data that has been loaded from the stage area. Functionally, it operates as a raw data vault and is restricted to containing only temporary (stage) tables and those tables that strictly align with base data vault types. The specific table types permitted within this layer include:

-   Hubs

-   Links, which encompass Historized Links (LINK), and Non-Historized Links (referred to as XLINK)

-   Reference Tables, which include Historized Reference Tables (REF), and Non-Historized Reference Tables (XREF)

-   Satellites, which very based on their parent entity, including HUB or Ref Satellite (SAT), Multi Active Satellite (MSAT), Link Satellite (LSAT), and Effectivity Satellite.

In terms of mandatory relationships, Hub, Link and Reference Tables are designated as parent entites and are required to have at least one child entity, which must be a Satellite. The only exception to this rule applies to non-historized entites (XREF and XLINK), which are allowed to hold attributes directly without requiring a satellite child. Conversely, every Satellite entity is constrained to having exactly one parent table.

#### 2\. Required System Fields and Key Generation [](https://data-engineering-docs-52075d.pages.roche.com/docs/data-modeling/data-vault/raw-dv-layer/rdv-layer/#2-required-system-fields-and-key-generation)

While flexibility is offered - allowing data to be modeled using a custom tool - it is mandatory that every table in this layer includes a core set of required system fields. These fields are vital for maintaining data warehouse consistency and integrity:

| System Field | Function and Definition |
| --- | --- |
| `_KEY` | This field holds the surrogate primary key. It is generated by applying a hashing function to the value of the business key(s). The values in `_KEY` must be unique within the table. |
| `_BKEY` | This field stores the non-hashed combination of the Business Key column(s). These are the columns used as the source input for generatign the `_KEY` hash. |
| `SYS_LOADED_ID` | This provides a consistent timestamp indicating the precise moment the data became available to the data warehouse. |
| `SYS_DATA_SOURCE` | This field documents the original source of the business key. It must specify the source object at the lowest level possible, such as a file or table. (e.g "SAP06.FINANCE.GL") |
| `SYS_SOURCE_ENV` | This tracks the envrionment from which the data was ingested ( e.g PROD) |
| `SYS_LOADED_FROM` | This identifies the specific source of the data located withing the stage layer (e.g PSA_SAP06.SAP06_/BIC/PLCMATSAL) |
| `SYS_HASH` | This field stores an MD5 hash value calculated from the table columns. This value corresponds to the HASH_DIFF concept used in standard Data Vault methodology |

For modeling this layer, the use of Data Vault Automation is currently recommended. This tool enables the modeling of data vault object by referencing metadata tables residing in the PSA layer. A major advantage of this recommendation is the tool's ability to generate the necessary DDL files and either Snowflake procedures or dbt files, which can then be used to directly populate the layer.

#### 3\. Schema Evolution [](https://data-engineering-docs-52075d.pages.roche.com/docs/data-modeling/data-vault/raw-dv-layer/rdv-layer/#3-schema-evolution)

The process of data ingestion is designed to be comprehensive, meaning the job always extracts all available columns from the source table or view, based on the definition active at the time of execution.

Initially, the ingested data is held in the Persistent Staging Area (PSA) layer, where it is stored in the JSON formati. While the PSA uses JSON, the subsequent Raw Data Vault (RDV) tables must precisely match the column structure of the iriginating source table.

To ensure data integrity and structural consistency, the system requires monitoring of the PSA layer's data structure. Should any change be detected in the source structure, an alert must be generated. When such a structural change occurs, the corresponging RDV target table must be updated or adjusted to reflect the new structure, or a new target table must be created entirely. A strict requirement of the process is that ALL columns retrieved from the source must be transferred into the RAW DV layer.

#### 4\. Data Retention Policy [](https://data-engineering-docs-52075d.pages.roche.com/docs/data-modeling/data-vault/raw-dv-layer/rdv-layer/#4-data-retention-policy)

In the current operational state, no specific data retention requirements are mandated or expected. By default, this means that all data ingested is kept indefinitely. However, the decision regarding the appropriate data period that holds value to the consumers is ultimately left to the data product teams to determine.
